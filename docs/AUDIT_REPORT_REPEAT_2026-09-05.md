# ObjectMemory 独立重复审查报告（2026-09-05）

本报告是在上一份 [`AUDIT_REPORT.md`](AUDIT_REPORT.md) 之后，对当前工作树重新执行的真实性、安全、存储和稳定性复审。它不替代上一份报告，也不重复计算上一轮已清除的 528 条事件。

## 一、结论

重复审查仍未发现规范 REAL 数据库存在假事件：`data/database/objectmemory.sqlite` 当前 `movement_events=0`，事件审计分类总数为 0，`unknown=0`。这不等于真实物品闭环已经通过；截至本报告，物理摄像头只证明可持续取帧和释放，真实手机确认移动仍为 0。

本轮确认并修复了六个高风险问题：

1. **P0/P1 来源冒认边界**：网络流曾使用容易被理解为物理摄像头已验证的文案；ESP32 事件仅凭上报字段仍可能被抬升；旧屏幕采集授权可能复用。现在网络源只显示“已收帧、物理来源未验证”，ESP32 必须与固件注册表和硬件验证字段一致，屏幕采集每次创建、修改、测试和启动都要使用本机同会话的单次短时授权。
2. **P1 跨进程模式与退出竞态**：两个进程可能同时操作同一模式数据，固件后台线程也可能在模式锁释放后继续写数据库。现在 REAL/DEMO/TEST 使用操作系统文件锁；活动目标拒绝跨模式清空；关机先有界等待固件 worker，超时则继续持锁直到旧 worker 排空。
3. **P1 当前状态证据竞态**：确认事件之后到达的较新普通观察可能令 `evidence_event_id` 变空；DEMO 页面因此只显示“最后看到”而遗漏上一条模拟确认。现在较新观察只更新观察字段，不抹掉最近确认链接；事件事务会在不倒退 `last_seen_at` 的前提下原子附加确认证据，页面同时诚实显示主状态和上一条确认来源。
4. **P1 审计清理旧计划竞态**：旧 dry-run 计划过去可能在事件后来被固定、人工纠正或成为当前状态证据后继续删除。现在 apply 先同时持有数据库所属模式和目标事件模式的跨进程租约，再重新审计，并在 `BEGIN IMMEDIATE` 内第三次核对保护条件；活动模式、来源不明自定义库或已变化目标一律 0 删除。
5. **P1 浏览器摄像头退出竞态**：WebSocket 关闭时旧引擎可能短暂重新显示为 `stalled`，来源会话也可能残留 `streaming`。现在先同步撤销发送者、撤下旧 generation、发布 STOPPED 并封存旧 source session，再在锁外等待资源线程；旧代际晚回调和旧清理都不能覆盖新代际。原竞态用例连续压力运行 20/20 通过。
6. **P1 E2E 误清理竞态**：一次瞬时健康请求失败过去可能被当成后端已经退出。现在隔离目录只有在收到 FastAPI lifespan 与模式锁释放后的启动器确认，并连续三次健康检查失败后才会删除。

项目目前达到：诚实的 REAL 空状态、明确隔离的 DEMO、稳定物理取帧、真实后端和 SQLite 的无源 E2E。项目尚未达到“真实手机从区域 A 移到 B 并由物理摄像头生成完整证据事件”的 P0 完整真实演示状态。

## 二、真实性与模式复审

- REAL、DEMO、TEST 的数据库和媒体目录仍独立；新增跨进程模式租约防止同一数据根被并发打开。
- REAL 无摄像头浏览器 E2E 使用真实 FastAPI 和独立 SQLite，事件、当前状态、轨迹、媒体、源会话均为 0。
- DEMO E2E 使用真实 FastAPI、独立 DEMO SQLite 和实际视频文件，恰好生成 1 条 `DEMO/video_file/is_simulated=true` movement、1 张截图、1 段短片。
- 浏览器 Mock 套件仍存在但仅由 `playwright.mock.config.ts` 单独运行，6 项结果只计为界面契约。
- 当前 REAL 搜索对不完整 provenance、模拟来源和未验证旧事件保持 fail-closed。
- 摄像头重连会封存旧 `source_session_id` 并建立新边界，旧会话候选不得跨重连确认。
- 普通网络流“能读帧”不再被写成“真实物理摄像头已验证”。

## 三、存储与删除复审

规范 REAL 数据库已经为空，因此本轮数据库清理 dry-run 和 apply 的事件删除数均为 0；没有把上一轮的 528 条再次计为本轮成果。

本轮三次安全清理共执行 242 个文件实例删除、6,680,171 字节；其中部分缓存与 SQLite sidecar 是前一次清理后由最终全量测试重新生成，因此这里记录的是实际删除操作，不冒充 242 个唯一历史文件。另删除两个失败 E2E 遗留锁文件和一个单元测试停机标记，共 159 字节；合计释放 6,680,330 字节。没有删除主数据库、唯一预审备份、用户参考图、当前报告、固件源码或仍被测试引用的图像。

同口径磁盘快照：初次审计前项目共 20,091 个文件、691,511,984 字节，`data` 为 1,537 个文件、79,629,119 字节；本次最终快照为 18,552 个文件、647,916,616 字节，`data` 为 35 个文件、14,245,152 字节。总差值还包含初次审计的事件媒体清理、构建与测试产物变化，不能全部归因于本轮累计 6,680,330 字节安全清理。最终快照见 [`after-reaudit.json`](../audit/after-reaudit.json)。

RetentionService 的复审修复包括：

- MINIMAL 和磁盘压力的“最近两条”只计算 `confirmed + confirmed_placed` 的 movement，候选或遮挡记录不能挤掉有效历史；
- BALANCED/FORENSIC 的过期媒体清理保留确认事件元数据；
- 真正删除前在 `BEGIN IMMEDIATE` 中重新核对 pinned、当前状态证据、人工纠正链和最近两条；
- Windows junction、symlink、断链和 reparse point 都不会被清理器跟随到数据根外。
- 审计器与快照器不再用普通只读连接打开源库：无非空 WAL 时走 immutable 内存快照；存在已提交 WAL 时稳定复制 DB+WAL 到系统临时目录并校验指纹、哈希和完整性。清理 SQLite sidecar 前同时持有运行模式锁和数据库独占句柄，活动数据库会在删除任何文件前整体拒绝。

逐项结果见 [`cleanup-reaudit.json`](../audit/cleanup-reaudit.json)。

## 五、诚实记录的失败与修复

- REAL E2E 曾两次在测试结束清理时因运行锁文件仍被占用而失败。最终机制改为测试先写关机标记，且只有收到 FastAPI lifespan/模式锁释放确认并连续三次健康检查失败后才删除隔离目录；最新复跑正常退出并通过。
- DEMO E2E 曾暴露当前状态证据链接竞态；修复数据库事务合并规则后，不再倒退较新观察，也不会丢掉已确认事件。
- DEMO E2E 随后暴露页面只显示较新“最后看到”、遗漏上一条模拟确认；修复为同时显示两个不同语义，最新复跑通过。
- 独立完整 Python 回归首次运行发现 5 个被窄范围定向套件遗漏的失败：4 个审计清理兼容/保护语义失败和 1 个浏览器关闭竞态。修复后完整套件实跑 204/204；浏览器竞态用例另做 20 轮连续压力验证。
- DEMO 循环视频 E2E 一度在下一轮已经回到桌面时仍断言当前状态必须是沙发。事件本身始终只有 1 条正确“桌面→沙发”确认；测试已改为分别验证“当前最后看到”和“上一条模拟确认”，复跑通过，没有修改生产状态机来迎合测试。
- 所有失败均保留在结果说明中，没有把失败尝试计入通过数字。
