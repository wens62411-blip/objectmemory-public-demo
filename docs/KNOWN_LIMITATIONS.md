# 已知限制

本文只列当前仍存在或本轮没有真实验证的边界。测试、代码存在和页面展示不能替代对应实测。

## P0：真实性验收尚未闭环

- 09-06 完整手机背面未检出与低帧率是历史失败记录。09-08 电脑摄像头已产生 1 条真实“最后看到”状态、1 张哈希核验截图，随后为 lost；历史移动事件仍为 0，手物关系只确认靠近，尚未通过真人拿起、放下五秒闭环。严格浏览器样本约 29.3–29.4 次/秒解码、28.0–28.4 次/秒画面变化，20 FPS 通过、严格 30 FPS 未通过，不能把识别或性能称为全面解决。见 [当前修复验收](CORE_VISION_3D_FIX_REPORT.md)。
- 当前 [P0 物理验收记录](../audit/p0-real/acceptance-runs.json) 仍为 `NOT_RUN`、`user_executed=false`；没有用真实物品完成本轮完整“起点 → 跨区移动 → 终点重新稳定”验收。工具、回归测试通过不等于这项物理验收通过。
- P0 使用服务端冻结的 14 个顺序场景：4 个负样本与 10 次交替 A/B 移动。每个套件场景槽位不可重试，失败/取消不能通过前端挑选历史成功记录替换；只有完整套件中的 10 次移动至少 8 次正确且 4 个负样本全部通过，才满足门槛。物理静止 5 分钟、同区微调、遮挡、断流重连和移动仍需操作者实际完成。
- 当前 `aruco_screen_validation` 的确认事件要求独立 `before` 截图、独立 `after` 截图和一段覆盖移动前后各至少 5 秒的短片，三者与同一个来源会话、帧范围、轨迹和实际哈希绑定；它不再使用一张左右拼图代替两张证据。普通非 P0 自动事件仍可采用 `contact` 合成主图，不能据此误述 P0 格式。合成 ArUco 帧通过这套门槛，只证明软件检查有效，不证明用户已执行物理动作。
- OpenCV 数字索引能打开并持续输出变化帧，不足以证明它是物理镜头；系统虚拟摄像头或 OBS 也可能占据该索引。操作者仍需确认预览对应其选择的物理镜头及当前物品。取流稳定性结果不能自动计入物理身份或物品识别验收。

## P1：识别、硬件和安全

- ArUco `DICT_4X4_50` 是当前可靠演示路径，需要可见标签；太小、模糊、折叠、反光或完全遮挡会失败。它不是“无标签 AI”。
- 实验模式已改为 NanoDet 候选 + DINOv2-small 多视角参考特征，不再以颜色直方图兜底。仍没有真实家庭手机/钥匙/钱包的精确率、召回率、低光和同类物品混淆基准，不能宣称成熟识别产品。
- 09-06 手机专项的公开视频单照片测试与当时的用户手机失败见 [历史报告](PHONE_RECOGNITION_FIX_REPORT.md)。09-08 已有用户手机的真实最后看到证据，但单次检出不能证明各种视角、遮挡、同类物品区分或完整动作准确率。
- 手部动作已接入本地 21 点、多帧几何姿势、持续手身份、手物共同运动与可见分离判断，详见 [手部动作说明](HAND_ACTION_GUIDE.md)。它不是触觉抓握分类器；公开照片、合成轨迹和实时输出不能替代标注的真人拿放准确率测试。
- 多摄像头各自取流和跟踪，但没有做跨房间同一物品的全局身份融合，也没有大规模并发相机稳定性验收。
- 09-08 已获授权对 COM3 XIAO ESP32S3 Sense 完成一次真实刷写，收到 OMACK 和启动日志，但 Wi-Fi 多次 reason 202，120 秒内没有 OMREADY；收据保留 flashed，联网设备 0。热点已实测 2.4 GHz 信道 11；SDK 支持 WPA3 SAE，错误不足以单独断定密码错或 WPA3 不兼容。待本地重新填密码后只重新配网，尚无板端取流、心跳或断电恢复验收。真实回执见 [物理安装记录](../data/verification/hardware-closure-20260908/physical-install.json)。
- 当前固件仅承担采集和设备协议，Windows 主机仍负责推理、轨迹、事件、数据库、媒体与界面。它不是无需电脑持续运行的独立家用成品；采购兼容开发板不会消除这一限制。
- ESP32 的网络 claim、设备自报信息、在线心跳和流 URL 只能建立 `unverified/esp32_unverified` 记录，不能证明物理板或绑定 REAL 摄像头；目前也没有用真机走通“本机合格 USB 串口 + 匹配 `OMREADY`”升级流程。
- USB flash、串口 provision 和 install 只允许 REAL；DEMO/TEST 禁用面向物理设备的申领入口，且后端拒绝物理串口操作。隔离的虚拟设备仍可在 DEMO/TEST 走模拟配对。固件 build 不受此限制，但编译仍不等于刷写。
- ESP32 固件的设备信息、截图和视频端点已增加独立 HMAC 派生读取凭据，移除通配 CORS；健康状态仍可无凭据读取，尚未在本块 XIAO 上完成端到端验收。未配置或联网认证失败后的 pairing AP 仍是开放热点，配置页为 HTTP；USB 与 AP 并发写配置尚未完整串行化，应避免同时提交。只适合可信隔离 LAN，不能公网暴露。
- Web 管理端默认 localhost、LAN 有短期管理员访问码和 Cookie，但没有 TLS、企业账号、细粒度角色、磁盘加密或公网防护。LAN 模式只用于可信家庭网络。
- 默认 localhost 启动不能直接让 ESP32 访问。当前设备安装/配网会在任务创建及硬件步骤前验证本进程实际 LAN 监听，并拒绝错误端口或非本机后台地址；需停止服务后用 `scripts/start.ps1 -Lan` 重启。页面 LAN 地址是候选，尚未证明开发板、Wi-Fi、路由器隔离或防火墙端到端可达。纯编译/纯 USB 刷写不受此 LAN 前置条件限制。
- 摄像头连接配置与媒体保存在本机，依赖 Windows 用户目录权限。虽然日志会脱敏常见凭据，用户仍应避免在名称、截图或导出中包含密码/token。

## P1：存储与长期运行

- `MAX_STORAGE_MB` 是受管理数据软上限。若剩余数据全部 pinned、当前状态证据或每件物品最近两次确认事件，服务会报告仍超限而不会越界删除；管理员需人工处理。
- `FORENSIC` 实际上保留每件物品最多 1000 个确认事件，不是无限；磁盘上限仍生效。
- BALANCED 超期媒体可被删除并把事件标为 `media_expired`。这种元数据不能再作为具有完整截图/短片的确认证据。
- SQLite 使用 WAL、busy timeout 和有限重试，适合单机工作负载；没有多主、远程数据库或高并发写入保证。
- 稳定性只能按当次真实运行窗口、输入源和配置判断，不能从一次 30 分钟或 60 分钟运行外推到任意天数、相机数量及网络条件都无泄漏。具体内存、线程、帧队列、磁盘和关闭结果以 [本轮稳定性记录](../audit/p0-real/runtime-stability.json)、[首次失败记录](../audit/p0-real/runtime-stability-first-attempt.json) 与 [审计报告](AUDIT_REPORT.md) 为准；本页不复用旧轮次数字充当新的最终结果。

## P2：摄像头和环境兼容

- 当前预览目标 30 FPS 与实际采集、实际预览、识别频率分别统计。2026-09-06 手机专项的 300 个暖机样本中，预览中位 28.67 FPS，但 44 个样本低于 20 FPS、最低 14.34；识别中位 5.38 FPS。本次 30 分钟探测因合盖待机存在 231.659 秒末尾采样缺口，不能算连续 30 分钟通过，详见 [手机专项实测报告](PHONE_RECOGNITION_FIX_REPORT.md)。新帧号可以递增但静止传感器图像仍可能相同，不能把相同 JPEG 当作更多不同画面。
- 手机二维码实际生成和截图解码已验证，电脑通过自身 LAN 地址的登录流程也已验证；没有实际拿用户手机完成跨设备连接。HTTP LAN 可以查看页面，但手机浏览器摄像头权限通常要求安全上下文；查看物品与把手机当采集摄像头是不同功能。

- 当前网络源安全校验要求 URL 中使用字面量私有/回环/链路本地 IP；局域网域名、IPv6 复杂形式和部分厂商重定向可能被拒绝。
- 没有对具体 RTSP、ONVIF、第三方 MJPEG 或真实 ESP32 型号完成本轮真机测试。RTSP/ONVIF/MJPEG 只表示配置的视频流，不证明摄像头厂商、型号或物理身份；当前 REAL 中只能形成“最后看到”观察，不能生成确认放置。ONVIF/认证/媒体 profile 的厂商差异仍可能导致失败。
- 浏览器摄像头实现了用户手势授权、二进制 JPEG 推送和释放，但服务端无法证明客户端 JPEG 确实来自物理 `getUserMedia`。因此 REAL 中 `browser_camera` 只能显示“最后看到 / 来源未验证”，不能成为确认放置；本轮也没有完成物理浏览器授权验收，组件 Mock 不算真机验证。
- 授权屏幕采集只抓固定矩形。窗口移动、遮挡、最小化、DPI/缩放变化和系统通知都会改变内容；没有基于窗口句柄的持续边界跟随，也不支持未经用户选择的区域。
- 默认 pip OpenCV 通常走 CPU；没有保证 CUDA/GPU 推理。硬件性能、分辨率和相机数量会直接影响实际 FPS。

## P2：事件语义和体验

- `confidence` 当前是启发式检测分数，不是校准后的正确概率。ArUco 后端的固定基数/尺寸项可能给孤立候选较高分；必须依赖连续稳定观察和完整移动证据，不能把 0.93 表述为“93% 准确”。

- “最后确认放置”表示最后一次满足证据门的位置，不是实时定位保证。物品可能在视野外被再次移动。
- 当前状态区分确认放置、最后看到、遮挡和丢失，但无法知道遮挡后真实去向；系统不会猜测靠垫下等位置。
- 人工纠正被明确标记为 `human_corrected`，它表达用户输入，不是算法检测。取消固定后可按普通 retention 删除。
- 区域边界与摄像头安装变化会影响位置语义；移动摄像头后应重新绘制区域并重新建立基线。
- 手机伴侣需要页面打开且用户先启用音频。锁屏、浏览器后台冻结、系统静音、振动能力和页面关闭都可能阻止响铃；没有原生推送服务。

## P2：测试覆盖

- Windows 启动器当前采用单进程 Selector 事件循环规避本地 Proactor 关闭异常路径；它不适用于需要 asyncio 子进程/管道的未来功能，并受 Windows 约 512 个 socket 的限制。当前固件与编码使用常规子进程而非 asyncio 子进程，不能据此宣称可扩展到企业高并发。边界参考 [Python 平台支持说明](https://docs.python.org/3/library/asyncio-platforms.html#windows)。

- Mock UI 契约测试仍保留，用来检查页面状态，不是核心链路证明。
- 真实 FastAPI/SQLite REAL E2E 可以证明无源零事件和模式隔离；DEMO 视频 E2E 可以证明文件视频的软件闭环；两者都不能证明物理摄像头识别。
- 硬件权限可以在浏览器自动化中模拟，但核心业务 API、最终事件、SQLite 和媒体不应被 Mock。最终测试分类和本轮退出码见 [审计报告](AUDIT_REPORT.md)。

## P3：后续方向

- 若后续将 P0 之外的普通自动事件也用于独立取证，可再明确其合成主图与独立 before/after 的格式及保留成本；P0 路径本身已经要求两张独立截图，不应重复列为尚未实现。
- 对真实家庭物品建立有标签与无标签的分场景误报/漏报基准。
- 真机验证固件已实现的视频读取认证，并给回退配网增加更强的物理/时间门控。
- 为多摄像头增加明确的跨源身份交接协议和可复现实验。
- 增加真正的窗口句柄授权采集、TLS 和更完整的本地账号/恢复策略。

## 当前明确不能宣称

- “真实摄像头已经识别手机并确认放到沙发”；
- “完全无标签 AI 识别已经可用”；
- “XIAO 已联网绑定、已真机取流或断电恢复已验证”（单次真实刷写已经成功，应与这些未完成项区分）；
- “ESP32 网络 claim 或在线心跳已经证明物理板并绑定真实摄像头”；
- “浏览器上传帧、RTSP、ONVIF 或 MJPEG 地址本身证明了物理摄像头身份”；
- “OpenCV 索引取到帧，就证明是物理镜头或已经完成手机移动验收”；
- “LAN 候选地址已证明 ESP32 可达，或买到开发板就能脱离电脑独立使用”；
- “虚拟设备等于物理硬件”；
- “测试视频事件来自真实家庭摄像头”；
- “所有摄像头型号、局域网和长期运行均已验证”。
